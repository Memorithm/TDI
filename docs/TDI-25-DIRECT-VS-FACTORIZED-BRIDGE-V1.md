# TDI-25 direct vs factorized torsor bridge v1 (slice 32)

Status: Phase-D Development/Validation software monitor. Contract
`tdi25-direct-vs-factorized-bridge-v1`. No training, no protected/final
access, no confirmatory execution and no scientific claim. No configuration
freeze pin is introduced or changed; holdouts are untouched.

## Population and budget

The monitor reuses the unchanged matched population
`tdi25-matched-reference-population-v1` (see `TDI-25-MATCHED-REFERENCE-V1.md`)
and the Stage-C preflight budget: every required family (TorsorFavorable,
ChiralFavorable, Mixed, Neutral), seed blocks `0..seed_blocks` (at most 2) and
`cases_per_block` cases (2..16) per block, in that canonical order. Cases are
generated by the v1 protocol only; there is no filtering or retry.

## The two bridge forms

Both forms are the upstream TDI-22 pairings under contract
`tdi22-torsor-dual-pairing-v1`; no transport or pairing logic is copied.

- **Factorized (reference)**: the unchanged matched T6 score,
  `(v + Q x omega).R + omega.C` with origin-reduced moment `C = M(P) + P x R`
  (`factorized_pairing`, via `torsor_arm_score`). It is reused from the matched
  primary run and re-checked bit for bit against `factorized_pairing`,
  together with its match bit.
- **Direct**: `v.R + omega.M(Q)` with the Varignon convention
  `M(Q) = M(P) + (P - Q) x R` (`direct_pairing`).

Both consume the same six query, six key and six geometry scalars with the
same zero trainable parameters, updates, readout and tolerance
(`ParameterReadoutCapacity::reference_t6()` on both sides).

## Monitored equivalence and rejections

Each case records both scores, the residual `factorized - direct`, whether
the two forms agree bit for bit, and both match bits against the
evaluator-owned common target. The equivalence must hold within the shared v1
relative tolerance `1e-12 * (1 + max(|factorized|, |direct|))`
(`BRIDGE_EQUIVALENCE_RELATIVE_TOLERANCE`, which is the existing
`TRANSPORT_IDENTITY_RELATIVE_TOLERANCE` / matched-reference scalar tolerance;
no new numeric value is introduced). Violations are rejected as
`bridge_residual`. The validator also recomputes the residual
(`residual_drift`) and the bit-identity flag (`bit_identity_drift`), and
requires bit-identical scores to share their match bit (`match_bit_drift`).

Validation also rejects contract, population, TDI-22 torsor-contract or
tolerance drift, capacity mismatch, case-count or canonical-order drift,
tampered family summaries, and any protected/final access, training or
scientific-claim flag. Protected/final split labels never generate a case.

## Recorded degeneracies

1. **Bit-exact population.** The v1 matched population draws every scalar from
   the half-integers `{-2.0, -1.5, ..., 1.5}`. Every product and sum in both
   forms is therefore exact in `f64`, and the monitored residual is identically
   zero on every case (smoke budget: 64/64 bit-identical on Development and on
   Validation, `max_abs_residual = 0`). The tolerance path is not exercised by
   this population; it is exercised only by an off-population hand-calculated
   test with non-dyadic carriers, where the two forms round differently and
   the residual is accepted under the tolerance rather than bit equality.
2. **Direct form is the torsor oracle.** The TorsorFavorable common target is
   itself the upstream direct pairing, so the direct side matches that target
   by construction. Agreement of the two forms on TorsorFavorable is thus a
   restatement of the TDI-22 algebraic identity, not independent evidence.
3. Chiral and Neutral populations set `P = Q = 0` by protocol, so both forms
   reduce to `v.R + omega.M(P)` there.

## What is recorded

Per case: factorized and direct scores, residual, bit-identity flag and both
match bits. Per family: case count, factorized matches, direct matches,
bit-identical cases and maximum absolute residual. These are software
diagnostics; interpreting them as attribution evidence is reserved for the
Stage-D attribution audit (slice 40).
